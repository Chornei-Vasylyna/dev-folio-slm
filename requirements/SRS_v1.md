# Специфікація вимог до програмного забезпечення (SRS) v1

**Проєкт:** DevFolio
**Версія документа:** 1.0
**Дата:** 12.10.2026
**Стандарт-основа:** ISO/IEC/IEEE 29148:2018 (скорочена структура)

## 1. Вступ

### 1.1 Призначення
Документ описує вимоги до веб-застосунку DevFolio – платформи, де розробники створюють онлайн-портфоліо, а відвідувачі (рекрутери, колеги) переглядають їх і завантажують резюме у PDF.

### 1.2 Бізнес-вимоги (для чого створюється система)
- BR-01. Дати розробнику спосіб оформити професійне резюме за кілька хвилин без верстки.
- BR-02. Дати рекрутерам єдине місце для пошуку розробників за спеціальністю та навичками.
- BR-03. Забезпечити експорт резюме у PDF для пересилання та архівування.

### 1.3 Межі системи
У межах: реєстрація та вхід, редагування портфоліо, каталог і пошук, публічне резюме, PDF-експорт, завантаження зображень.
Поза межами цієї версії: чати та повідомлення, адміністративна панель.

### 1.4 Терміни
| Термін | Значення |
|--------|----------|
| Портфоліо | Набір даних користувача: профіль, досвід, освіта, навички, проєкти |
| Публічне резюме | Сторінка `/resume/{id}`, доступна без входу |
| RLS | Row Level Security – політики доступу до рядків у Supabase |

## 2. Загальний опис

### 2.1 Користувачі
| Роль | Опис |
|------|------|
| Відвідувач | Переглядає каталог і резюме, шукає, завантажує PDF. Вхід не потрібен. |
| Автор профілю | Зареєстрований розробник; має всі можливості відвідувача й редагує власне портфоліо. |

### 2.2 Зовнішні системи
- Supabase – автентифікація (email/пароль, Google, GitHub) і база даних (таблиці profiles, experiences, education, skills, projects).
- Uploadcare – зберігання зображень (фото профілю, зображення проєктів).

### 2.3 Технологічний контекст (обмеження)
Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4, react-hook-form + Zod, @react-pdf/renderer, менеджер пакетів pnpm. Змінні середовища: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_UPLOADCARE_PUBLIC_KEY`.

### 2.4 Припущення
- Резюме за посиланням `/resume/{id}` вважається публічним (у коді немає перевірки автентифікації для цього маршруту).
- Дані профілю в каталозі читаються без входу.

## 3. Функціональні вимоги

Нумерація збігається з `requirements.md`.

### FR-01. Автентифікація
- 1.1 Реєстрація за email і паролем.
- 1.2 Вхід за email/паролем, через Google та через GitHub.
- 1.3 Вихід із системи.
- 1.4 Авторизований користувач, який відкриває `/login` або `/register`, перенаправляється на головну.
- Перевірка: сценарії US-04; відкрити `/login` після входу.

### FR-02. Редагування портфоліо
- 2.1 П'ять вкладок: Profile, Experience, Education, Skills, Projects; кожна має власну форму.
- 2.2 Profile: аватар, ім'я, спеціальність, email, телефон, GitHub, LinkedIn, Telegram, біографія.
- 2.3 Experience / Education: список записів (посада/спеціальність, компанія/заклад, період, опис); записи можна додавати й видаляти.
- 2.4 Skills: перелік навичок через кому; зберігається як окремі записи.
- 2.5 Projects: назва, опис, посилання GitHub та Live Demo, зображення.
- 2.6 Завантаження зображень через Uploadcare (клік або drag-and-drop).
- Перевірка: US-01, US-05.

### FR-03. Каталог і пошук
- 3.1 Головна сторінка показує картки розробників (аватар, ім'я, спеціальність, навички) та кількість зареєстрованих користувачів.
- 3.2 Пошук за ім'ям, спеціальністю та навичкою без урахування регістру; порожній запит повертає всіх.
- Перевірка: US-02.

### FR-04. Публічне резюме
- 4.1 Сторінка `/resume/{id}` без автентифікації.
- 4.2 Розділи: About, Experience, Education, Skills, Projects, Contacts; порожні розділи не показуються.
- 4.3 Бокова навігація за розділами.
- 4.4 Якщо профілю з таким id немає – відповідь 404.

### FR-05. PDF-експорт
- 5.1 Кнопка Download формує PDF у браузері й зберігає файл `{Ім'я}_resume.pdf`.
- 5.2 Символи `< > : " / \ | ? *` та пробіли в імені замінюються на `_`.
- Перевірка: US-03.

## 4. Нефункціональні вимоги

| ID | Категорія | Вимога | Метод перевірки |
|----|-----------|--------|-----------------|
| NFR-01 | Безпека | `/portfolio` та дії запису доступні лише автентифікованим | Тест: запит без сесії → редірект на `/login` |
| NFR-02 | Безпека / якість даних | Пароль 8–64 символи з малою, великою літерами та цифрою; обмеження довжини полів; телефон E.164; домени посилань | Ввід некоректних значень у форми |
| NFR-03 | Зручність | Діалог про незбережені зміни; повідомлення про результат збереження | Ручний тест |
| NFR-04 | Адаптивність | Коректне відображення 360–1920 px | Перевірка в DevTools |
| NFR-05 | Продуктивність | LCP ≤ 3 с на 4G при ≤ 100 профілів | Lighthouse, медіана 3 запусків |

Статус кожної вимоги (реалізовано або ціль) вказано в `requirements.md`.

## 5. Модель даних
Таблиці Supabase: `profiles`, `experiences`, `education`, `skills`, `projects`; кожна містить `user_id`. Для профілю використовуються поля: avatar, full_name, specialty, email, phone, github_url, linkedin_url, telegram_url, bio (точні назви стовпців – у `src/lib/supabase/database.types.ts`).

## 6. Відомі проблеми та ризики
1. Серверні дії приймають дані без повторної валідації (наприклад, `upsertExperiences`). Backlog: TD-01.
2. Збереження розділу виконується як "видалити все, вставити нове" без транзакції – ризик втрати даних. Backlog: TD-02.
3. У `proxy.ts` виводяться дані сесії в консоль. Backlog: TD-03.
4. Регістр імпортів не збігається з назвами папок (`get` / `GET`). Backlog: TD-05.
5. RLS-політики потребують перевірки. Backlog: TD-06.
